# V4 플랜: 근거 없는 정보 전달 최소화 + 근거 있는 개인화 회복

## Context

- v3R 최종 측정 결과(v0 대 v3R, 각 70건)
  - LLM 헤드라인은 75.7%에서 10.0%로 내려갔다.
  - 개인화 점수는 4.757에서 4.264로 떨어졌고, 하한 −0.650으로 비열등 기준 −0.3을 넘지 못했다.
- v3R에 남은 LLM 지적은 18건이다(최종 7건, 개발 11건). 원인은 다섯 가지다.
  1. fit이 다른 말을 근거로 승인했다: N014 · N028 · N035 · N038 · N047
  2. 페르소나 정보(고민 · 사용 시점 · 피부 타입 · 생활 장면)가 상품 이야기로 넘어갔다: F026 · F049 · F062 · N029 · N048 · N057
  3. 효능을 엉뚱한 출처에 붙였다: F038 · N001
  4. 제목에 근거 없는 시간 · 횟수 · 비교 표현을 넣었다: F028 · F038 · F047 · N031 · N042
  5. 사용량을 바꿨다: F058 · N035
- 개인화 하락의 절반 이상은 v3R이 페르소나 고민을 아예 빼 버린 15건에서 나왔다(4.83에서 3.63으로). 이 15건은 두 종류다.
  - (가) 상품이 그 고민을 다루지 않는 짝(약 6건): 정직하게 쓰면 잃는 점수
  - (나) 상품정보에 근거가 있는데도 뺀 경우(약 7건): 되찾을 점수
- 판정기(잠금)는 고민 공감을 보상하지만 그 공감에 근거가 있는지는 보지 않는다.
- 사람 확인 문제: 개발 시험에서는 같은 종류의 지적을 O로 봤고(9/9), 최종 시험에서는 X로 봤다(0/7).
- **목표**
  - 원인 1~5를 입력 차단, 연결 확인, 생성 뒤 점검의 세 겹으로 막아 근거 없는 주장을 v3R의 절반 이하로 줄인다.
  - (나)의 개인화를 되찾는다.
  - (가)는 사전 등록한 층별 지표로 정직하게 보고한다.
- **현실적인 기대치**
  - 개발 시험(140건): 주 지표 3~6건, 9개 유형 8~12건
  - 원인 ①과 ③은 0이 되지 않는다. 매 실행에 0~2건은 남는다고 보고 보고서에 적는다.

## 변경 1: 생성기 (운영 코드)

최종 버전 파일은 `persona_fit.py` · `purpose_prompt.py` · `generate_crm_message.py` · `product_fields.py`에 새 파일 `services/claim_check.py`를 더한 5개다.

### 1-1. 생성기 입력 줄이기 (원인 ②)
- **`build_persona_view(persona_info, purpose)` 추가 (`persona_fit.py`):** 생성 프롬프트에는 이름 · 나이 · 성별 · 직업만 넘긴다.
  - 생활 장면(라이프스타일)도 뺀다. F028 "하루 종일", N057 "회식 → 더부룩", N029 "촬영 후 답답"이 모두 라이프스타일 줄에서 나왔다.
  - **예외: 목적 7(라이프스타일/연령대 강조)에만 라이프스타일 줄을 넘긴다.** 이 목적에서 라이프스타일은 입력이 아니라 메시지의 내용 자체다. 이 목적에서 새는 표현은 1-4 생성 뒤 점검(한정 표현 · 공감 호출)이 덮는다. 개발 시험과 운영이 같은 규칙을 쓴다.
  - 평가용 자유 서술("라벨: 값" 줄)과 운영용 구조화 dict(`persona_client.py` 키)를 둘 다 처리한다. 처음 보는 라벨은 뺀다.
  - 페르소나 원문 전체는 fit 입력으로만 쓴다.
- **`build_fit_section()`:** 승인된 연결만 보여준다.
  - 고민 연결: "공감 표현(페르소나의 말) → 말할 수 있는 효과(근거 문구)"
  - 선호 · 구매 기준: "말할 수 있는 특성"
  - **연결 불가와 충돌 목록은 생성 프롬프트에 넣지 않는다.** 점검과 평가 저장용으로만 쓴다(1-4).
  - "사용 상황은 장면 묘사로만" 문구는 지운다.
- **`generate_crm_message.get_crm_prompt`:** 원래 `persona_info` 대신 걸러진 정보와 승인된 연결 안내를 넣는다. fit이 fallback · disabled이면 걸러진 정보만 넣는다.

### 1-2. fit 구조와 승인 확인 (원인 ①)
- **출력 형식:** LLM 출력(`FitOutput`)만 세 목록에서 `needs` 한 목록으로 바꾼다. 니즈마다 `status`(connectable · not_connectable · conflict)를 하나만 갖게 해서, 같은 니즈가 두 상태에 동시에 들어갈 수 없게 한다.
  - `verify()`는 `needs`를 기존 `FitResult`(connectable · not_connectable · conflicts) 형태로 바꿔 돌려준다.
  - `to_dict` · `from_dict`는 그대로 둔다. 그래야 저장된 v3R `fit_cache.jsonl`, `CachedFitter`, 단계 1(a)가 그대로 호환된다.
  - 새로 생긴 정보(`need_type` 확장, 연결 확인 결과)는 `FitResult`에 선택 필드로 더한다. 없으면 빈 값이다.
- **`need_type`:** `concern` · `preference` · `criterion`(구매 기준) · `usage`(사용 방식 · 시점) 네 가지로 둔다.
- **SYSTEM 기준:** "근거 문구가 니즈와 같은 결과 · 같은 속성을 말할 때만" 승인한다. 사례 문구는 넣지 않는다.
- **코드 차단 (`verify()`):** LLM 분류에 기대지 않는 두 겹이다.
  - `usage` 유형은 항상 연결 불가로 처리한다.
  - LLM이 다른 유형으로 분류했더라도, 승인 니즈나 근거가 페르소나 원문의 사용 방식 · 사용 상황 줄과 세 글자 이상 연속으로 겹치면 내린다.
  - 사용 시점과 사용량은 상품 필드로만 쓴다(1-3).
- **연결 확인 (독립 호출):** 승인된 연결마다 "이 근거 문구가 이 니즈와 같은 결과 · 속성을 말하는가"를 gpt-5-mini에 한 번 묻는다. 아니라고 하면 내린다. 연결끼리 병렬로 호출한다.
  - v3R2 후보 A의 필터(`fit_fix_check.py`)를 재사용한다.
  - 켜는 조건은 단계 1의 정확도 · 지연 기준을 모두 넘는 것이다.
  - **실패 시 동작:** 확인 호출이 예외 · 시간 초과로 실패하면 그 연결은 승인하지 않는다(내림). 확인되지 않은 연결을 통과시키지 않는다. 예외는 fit 안에서 처리해, 노드로 올라가지 않게 한다.
- 근거 문구가 스냅숏에 있는지, 필드 분류가 맞는지, 고민 어휘가 겹치는지 보는 기존 검사는 그대로 둔다.

### 1-3. 프롬프트 규칙 (원인 ③④⑤, `purpose_prompt.py`)
- **사용 정보:** 사용 시점 · 단계 · 사용량 · 횟수 · 적합한 피부 타입은 상품 필드(`usage_context`, `application_timing`, `how_to_use`, `skin_type`, `suitable_for`, `target_user`) 문구로만 쓴다.
- **효능 귀속:** 효능을 붙이는 대상의 범위를 "성분"에서 "성분 · 도구 · 구성품"으로 넓힌다. 서로 다른 문장의 효능을 합치지 않는다.
- **제목:**
  - 질문형 · 공감형 훅의 재료를 "고객의 고민"에서 "연결 안내의 공감 표현이나 상품 특징"으로 바꾼다.
  - 시간 · 횟수 · 양 · 비교 표현은 상품정보에 같은 표현이 있을 때만 쓴다.
- **베스트셀러 · 프로모션:** 연결 안내에 항목이 있을 때만, 그중 하나를 본문 한 문장에 쓴다(조건부).
- **입력이 사라진 줄 정리**
  - 목적 6(피부타입/고민): "1. 피부 타입 + 고민 → Hook"을 "연결 안내의 공감 표현(없으면 상품정보의 대상 고민 · 피부 타입)으로 Hook"으로 바꾼다. "2. 선호 성분 + 가치관"은 "연결 안내의 특성에 있을 때만"으로 바꾼다. "정보가 부족할 때"의 "사용 장면 묘사" 문구는 지운다.
  - 목적 7(라이프스타일/연령대): 넘겨받은 라이프스타일 줄만 쓰도록 바꾼다("세부 상황 · 가치관" 추출 줄은 지운다). 제품의 사용 시간 · 횟수 · 단계는 상품정보로만 쓰는 기존 줄은 유지한다.
  - 다른 목적의 "가치관이 겹치면 언급", "라이프스타일에 맞는 언어" 줄: 가치관은 연결 안내의 특성에 있을 때만 쓰게 하고, 라이프스타일은 "연령대"로 줄인다.

### 1-4. 생성 뒤 점검 + 최대 1회 재생성 (원인 ④⑤, ②의 일부, 사용 시점 오류를 덮는 안전망, 새 파일 `services/claim_check.py`)
- **잡지 못하는 것:** 원인 ③(효능 귀속 혼동)은 정규식으로 못 잡는다. 1-3의 프롬프트 규칙뿐이다.
- **범주 A, 근거 없는 한정 표현:** 제목과 본문에서 아래 범주의 표현을 찾는다. 상품정보 필드에 같은 표현이 없으면 걸린다.
  - 지속 시간: 시간 단위, "종일", "밤새" 류
  - 횟수: "한 번", "N회", "매일" 류
  - 양: 스푼 · 방울 · 펌프 · 소량 · 듬뿍 류
  - 비교 · 변화: "다른/다르게/달라", "변화", "차이" 류
- **범주 B, 근거 없는 공감 호출:** fit이 승인한 고민 연결이 0개인데 고민을 불러내는 표현이 나오면 걸린다. 예: 걱정 · 고민 · 신경 쓰이 · 불편 · 답답 류 + "~때 / ~라면 / ~시죠" 형태. N029 · N057처럼 지어낸 고민 장면을 겨냥한다.
  - **면제:** 호출 표현이 붙은 고민어가 상품 필드(`concern` · `suitable_for` · `skin_type` · `target_user`)와 세 글자 이상 연속으로 겹치면 통과시킨다. 목적 6의 정상 동작("상품정보의 대상 고민으로 시작")을 오탐하지 않기 위해서다.
- **범주 C, 연결 불가 니즈 재등장:** fit의 연결 불가 니즈가 메시지에 세 글자 이상 연속으로 나오면 걸린다.
- **범주 D, 근거 없는 사용 시점 · 단계:** 사용 시점 · 단계 표현이 상품 필드(`usage_context` · `application_timing` · `how_to_use`)와 세 글자 이상 연속으로 겹치지 않으면 걸린다. 예: "~전 / ~후 / 마무리 단계 / 젖은 ~ / 잠들기 전" 류.
  - 모델이 스스로 시점을 지어내는 경로를 막는다(v0의 "출근 전 샤워 후 5분" 류). 페르소나에서 오는 경로는 입력 차단이 막는다.
  - "전/후" 같은 일반어는 오탐이 많을 수 있다. 켜는 기준을 못 넘으면 꺼진다.
  - **미리 정한 보정 1회:** 오탐이 많으면(예: "세안 후 당김 없이"처럼 효능 문장 속 시점어) 면제 범위를 "상품정보 전체 필드"로 넓힌다. 넓히면 재현율이 조금 떨어지므로, 두 설정의 오프라인 숫자를 같이 보고 정한다.
- 사전은 범주 단어로만 만들고, 이번 사례 문장은 넣지 않는다.
- **재생성:** 하나라도 걸리면 생성을 1회 다시 한다. 다시 할 때는 걸린 표현을 빼라는 지시만 덧붙인다. 그래도 걸리면 두 번째 결과를 쓰고 `claim_check="still_hit"`으로 기록한다.
- **켜는 조건:** 범주마다 단계 1(a)의 오프라인 기준을 넘는 것만 운영에서 켠다. 넘지 못한 범주는 평가에서 진단용으로만 기록한다.
- **켜기 상태의 위치:** 켜는 범주 목록은 `claim_check.py` 안의 상수로 둔다(`settings.py`나 환경 변수가 아님). 그래서 최종 버전 5개 파일의 해시 잠금에 포함된다. 단계 2를 통과하면 켜진 목록을 AMENDMENTS에도 기록한다.
- **실패 시 동작:** 점검이나 재생성이 예외로 실패하면 첫 결과를 쓰고 `claim_check="error"`로 기록한다.
  - `generate_message_node`는 생성 전체를 try/except로 감싸고, 예외가 나면 모든 태스크의 메시지를 버린다(`nodes.py` 125~138행).
  - 그래서 점검과 재생성은 태스크별 `return_exceptions=True` 보호 안에서 돌린다. 한 태스크의 실패가 노드로 올라가지 않게 한다.
- **데이터 보관 방침**
  - `get_crm_prompt`와 `generate_crm_message`는 같은 노드(`generate_message_node`) 안에서 차례로 불린다. 태스크 dict는 그 노드의 지역 변수다.
  - state에는 `nodes.py`가 고른 필드(product_id · 상품명 · 목적 · message 등)만 들어간다. 이 파일은 잠금 파일이고 고칠 필요도 없다.
  - 연결 불가 니즈 문구, 겹침 계산, 점검 결과는 태스크 dict 안에서만 쓰고 state와 체크포인터 DB에는 남기지 않는다.
  - 운영 로그에는 걸림 여부와 범주만 남기고, 니즈 문구는 남기지 않는다.

### 1-5. 운영과 측정의 일치
- 운영 서버(`generate_server.py`)의 `PersonaFitter()` 주입은 유지한다. 연결 확인과 생성 뒤 점검은 생성기 안에 넣어 운영과 평가가 같은 경로를 탄다.
- 평가는 `RecordingFitter`(eval 쪽 감싸개)로 fit · 확인 결과를 저장한다. 운영 코드는 이 때문에 바꾸지 않는다.
- **측정하지 않는 운영 경로: 품질 게이트 뒤 재작성**
  - 운영에서는 생성 뒤 품질 게이트가 돈다. 통과 조건은 각 점수 3 이상, overall 4 이상이다(`settings.py` 207~208행).
  - 떨어진 메시지는 `apply_feedback_prompt.py`(52~57행)가 원본 페르소나 전체를 "수정 시 반드시 반영 · 피부 고민, 가치관, 라이프스타일에 맞게"라는 지시와 함께 받아 다시 쓴다. 최대 재시도 횟수까지 반복된다.
  - 따라서 V4가 막은 고민 · 라이프스타일이 재작성에서 다시 들어올 수 있다. 개인화가 낮은 (가) 짝에서 특히 그렇다.
  - 두 파일은 잠금 대상이라 V4에서 고치지 않는다.
  - 대응
    - (a) PREREG와 보고서에 "측정은 생성 단계 한정, 게이트 뒤 재작성은 별도 점검"이라고 범위를 적는다.
    - (b) 단계 2에서 게이트 · 재작성을 오프라인으로 점검한다(단계 2 참고).
  - 재작성이 근거 없는 주장을 늘리는 것으로 나오면, 잠금 파일 수정은 별도 플랜으로 다룬다.

  - 포트폴리오의 주 개선 수치는 같은 시점에 측정한 최종 시험의 v0 대비 값으로 한다.
